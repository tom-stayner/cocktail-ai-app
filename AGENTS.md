# Cocktail AI App

## Mission

Cocktail AI App is a Cloud & AI Engineering portfolio project.

The objective is to demonstrate professional software engineering practices while building a production-quality, cloud-native cocktail application using AWS and AI.

Code quality, maintainability, testing, and documentation are considered features.

---

## Engineering Philosophy

- Prefer maintainable solutions over clever ones.
- Prefer small, incremental improvements.
- Keep architecture simple until complexity is justified.
- Avoid unnecessary abstraction.
- Documentation is a first-class deliverable and should remain concise, accurate, and valuable.
- Treat code quality, testing, and documentation as part of every feature.

---

## Engineering Role

When working on this repository:

- Think like an experienced software engineer.
- Consider the wider impact of changes across the project.
- Review affected code, tests, documentation, and configuration before implementing changes.
- Think beyond the immediate file being modified.
- Explain significant architectural decisions and trade-offs.
- Verify work before considering a task ready for review.

## Engineering Workflow

For significant changes:

1. Review the current implementation and existing documentation.
2. Identify affected code, tests, documentation, and configuration.
3. Produce a brief implementation plan.
4. Obtain approval before implementing architectural or structural changes.
5. Implement only the agreed changes.
6. Update documentation where the change materially affects behaviour, architecture, configuration, or developer workflows.
7. Verify the implementation.
8. Summarise:
   - what changed
   - why it changed
   - how it was verified

When updating documentation:

- Clearly distinguish **Current Implementation** from **Future Direction**.
- Do not describe planned functionality as implemented.
- Preserve relevant future architectural direction where appropriate.

## Git and Delivery Workflow

This repository uses short-lived branches for approved implementation work.

### Delivery Roles

- **Product Owner — User:** approves scope, accepts or rejects changes, and authorises commits, pushes, pull requests, merges, branch cleanup, tags, and releases.
- **Solution Architect and Reviewer — ChatGPT:** proposes designs, prepares implementation briefs, reviews implementation summaries and actual diffs, and advises whether acceptance criteria are satisfied.
- **Implementer — Codex:** creates the approved working branch, modifies repository files within scope, runs verification, and presents the implementation summary and actual diff.

An implementation summary is not sufficient for acceptance when an actual diff is available.

### Branch Prechecks and Creation

Before modifying files for an approved implementation step:

1. Confirm the previous approved implementation step is present on local `main` and `origin/main`, where applicable.
2. Confirm the working tree is clean.
3. Switch to `main`.
4. Update local `main` using `git pull --ff-only`.
5. Confirm local `main` and `origin/main` are synchronized.
6. Confirm no unexpected commits or tracked generated artifacts are present.
7. Create a new short-lived feature branch from the updated `main`.
8. Confirm and report the active branch and base commit before implementation.

Branch naming convention:

```text
feature/<version>-step-<number>-<short-description>
```

Example:

```text
feature/v0.5.0-step-3-dependency-separation
```

Stop before creating the branch or modifying files if:

- the working tree is not clean
- local and remote `main` have diverged
- the previous approved implementation step is absent from `main`
- unexpected commits or tracked generated artifacts are present
- the approved branch already exists
- confirming the repository state would require assumptions

Do not merge, rebase, reset, restore, discard work, rewrite history, or alter existing branches to resolve a failed precheck without explicit Product Owner approval.

Do not:

- implement approved work directly on `main`
- create future implementation branches in advance
- reuse a completed step branch for a later step
- create a long-lived `develop` branch unless explicitly requested
- create release or hotfix branches unless explicitly requested

### Implementation Authority

Codex may:

- inspect repository status, history, branches, and diffs
- create the specifically approved feature branch after all prechecks pass
- modify files within the approved scope
- run tests and quality checks
- build temporary local verification artifacts when the brief permits them
- prepare a proposed commit message
- provide the actual diff for review

Codex must not, unless explicitly authorised by the Product Owner:

- commit changes
- push branches or commits
- open or modify pull requests
- merge branches or pull requests
- delete local or remote branches
- create, move, or delete tags
- publish releases
- deploy application code or infrastructure
- rewrite Git history

Authorisation for one action does not imply authorisation for a later action. For example, authorisation to commit does not authorise pushing, opening a pull request, merging, deleting a branch, tagging, or releasing.

### Scope Control

Implement only the approved brief.

If additional work is discovered:

- report it separately
- classify it as **required**, **recommended**, or **optional**
- explain its impact
- do not include it without approval unless it is strictly necessary to keep the approved change correct and buildable

If strictly necessary additional work changes the approved scope materially, stop and request approval rather than silently including it.

Avoid unrelated:

- formatting churn
- dependency upgrades
- renaming
- refactoring
- documentation rewrites
- cleanup

### Verification Before Handback

Before presenting implementation work for review:

1. Run the verification commands specified in the implementation brief.
2. Run the repository's established test, lint, and formatting checks where applicable.
3. Check `git status`.
4. Run `git diff --check`.
5. Review the complete actual diff for accidental, generated, sensitive, or unrelated changes.
6. Confirm generated review or build artifacts are not tracked.

Do not describe implementation work as approved, accepted, merged, deployed, released, or complete. Approval remains with the Product Owner after architectural review of the actual diff.

### Implementation Completion Report

Every implementation handback must include:

1. Current branch name and base commit.
2. Confirmation that the previous approved step is present in branch history.
3. Files changed.
4. Implementation summary.
5. Behaviour changed, including important behaviour intentionally left unchanged.
6. Design decisions and trade-offs.
7. Commands run.
8. Test, lint, formatting, and other verification results.
9. Warnings, assumptions, and unresolved risks.
10. Additional work discovered and its **required**, **recommended**, or **optional** classification.
11. Confirmation that generated artifacts are untracked.
12. Confirmation that no unauthorised commit, push, pull request, merge, branch deletion, tag, deployment, or release occurred.
13. The complete actual diff, or clear instructions for obtaining it.

If a review diff file is created, create it outside the repository. Do not add it to the working tree or Git index.

### Approval, Merge, and Step Closeout

After implementation and architectural review, the Product Owner decides whether to authorise:

- committing the approved changes
- pushing the feature branch
- opening a pull request
- merging the pull request
- performing post-merge branch cleanup

These actions may be authorised individually or as an explicitly defined group. Do not infer authority for an action that was not included.

After a pull request has been merged:

1. Confirm the working tree is clean.
2. Switch to `main`.
3. Update local `main` using `git pull --ff-only`.
4. Confirm local `main` and `origin/main` are synchronized.
5. Confirm the approved commit or approved changes are present on `main`.
6. Confirm no unexpected commits or file changes are present.
7. Delete the completed local feature branch using normal deletion, but only when branch cleanup was authorised.
8. Delete the remote feature branch only if it still exists and remote deletion was authorised.
9. Report the final branch, repository status, and synchronized `main` commit.

A merge commit created by GitHub is a valid pull-request outcome. The `git pull --ff-only` requirement controls synchronization of local `main` with `origin/main`; it does not require the pull request itself to use a fast-forward merge.

If `origin/main` already contains the approved work, do not perform another local merge.

A squash or rebase merge may cause normal local branch deletion to fail because the feature commit is not directly reachable from `main`, even when the approved changes are present. If normal deletion fails, stop and request explicit Product Owner approval before any force deletion.

Do not force-delete a branch, rewrite history, rebase, reset, restore, or discard changes without separate Product Owner approval.

Stop and report if:

- local and remote `main` have diverged
- the approved work is absent from `main`
- unexpected commits or file changes are present
- the working tree is not clean
- normal branch deletion fails
- confirming the merged state would require assumptions

### Next Implementation Step Gate

Do not create the next implementation branch until:

- the previous step is confirmed on synchronized local and remote `main`
- the previous feature branch has been cleaned up as authorised
- the working tree is clean
- the next implementation scope has been approved

Create the next branch from the newly synchronized `main`; never continue implementation on the previous step's branch.
